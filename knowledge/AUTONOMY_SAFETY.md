Активный режим — `raid.every_respawn: true`. Герои читают таймер
возрождения непосредственно в игре; получасовые окна больше не ограничивают
вход. При длительном откате продолжается обычный фарм. За пять минут до
ожидаемого возрождения агенты перестают начинать долгие задачи, проверяют
пещеру каждые 5–15 секунд и после открытия поддерживают готовность.
Если сбор длится дольше одного локального цикла, участник остаётся в зале.
Только Кейс начинает бой после проверки ID, класса и готовности всей тройки.
Посторонний игрок не заменяет отсутствующего участника.
После завершения или неопределённого результата новая попытка запрещена,
пока сервер не подтвердит закрытие/откат и последующее открытие живого босса.
Перезапуск процесса и местные часы сами по себе не разрешают повтор.
Дневной лимит попыток отключён; золото за дополнительные входы не расходуется.
Режим получасовых окон оставлен только для совместимости и офлайн-проверок.

Состояние попытки сохраняется до отправки старта. При возобновлении процесса
бой обслуживается раньше любых хозяйственных переходов. Отсутствие кнопок
или исчерпание локального лимита ходов не вызывает выхода из рейда.
Неоднозначный результат остаётся неоднозначным: победа не предполагается.
После 10 минут без боевой панели восстановление закрывается с неподтверждённым
результатом. История последних 20 попыток хранится в `state/<account>/runtime.json`.
Наблюдаемые урон и лечение — нижняя оценка по доступным строкам журнала:
одинаковые строки, повторные загрузки и неполный серверный журнал ограничивают точность.
HP цели не подменяется единственным значением HP самого героя.

Ограничение: проверка состава и нажатие старта — два разных серверных действия.
Игра не предоставляет атомарную блокировку состава; участник может потерять
сессию между ними. Нужна проверка реального совместного боя, прежде чем
решать, достаточно ли трёх героев.

## Башни, инвентарь и экономика

- Любая ненулевая или неизвестная усталость запрещает вход в башни.
  Непосредственно перед входом значение читается снова; фоновые входы
  используют тот же барьер. Сохранённая пауза не разрешает вход без свежего нуля.
- Автоматическое надевание отключено на границе драйвера, в том числе после
  почты и магазина. Мифические вещи нельзя разобрать или отправить на витрину.
  Массовый разбор без проверки каждой вещи отключён.
- Свитки выбрасываются; книги и неизвестные предметы не активируются.
  Распознанные сундуки с явной бесплатной кнопкой открытия обрабатываются
  при уборке инвентаря; неизвестные и платные подтверждения пропускаются.
- Алтарь обслуживается железом. Дополнительные бои, опыт и сброс усталости
  за золото запрещены. Оплачиваемый игровой LLM-советник отключён.
- Железо разрешено покупать только при известной необходимости ремонта,
  нулевом остатке железа и известной стоимости ремонта. Лимит одной операции
  и суток — 1 золото; дополнительно не более 50 серебра за предложение.
  Курс серебра к золоту не предполагается. Предпочтительны предложения
  без золота. Любая неясность цены/валюты на подтверждении запрещает покупку.
- До покупки резервируется весь дневной лимит. Успех проверяется по изменению
  железа и обеих валют. Неоднозначная отправленная покупка остаётся заблокированной
  даже после смены даты, пока её результат не проверен. Неотправленная или
  подтверждённая операция тоже не повторяется в те же сутки.
- В Actions резерв записывается немедленно в отдельный файл через GitHub Contents
  API с проверкой SHA. Без токена, при конфликте или сетевой ошибке покупка запрещена.
  Файл не перезаписывается итоговым коммитом дневных счётчиков.
  Локально используются атомарная запись и эксклюзивный файл блокировки.
- Дни бюджета считаются по UTC+3. При двух независимых локальных копиях одного
  аккаунта без общего состояния общий лимит не гарантируется: для игры должен
  работать один агент на аккаунт. Actions обеспечивают это группой concurrency.

## Безопасные проверки и ввод в эксплуатацию

```sh
python -m compileall -q barbars run.py
python -m pytest tests/test_safety_offline.py -q
```

`pytest.ini` ограничивает обычный сбор офлайн-набором: остальные файлы `tests`
содержат живые пробы и не должны запускаться общей командой.
Набор подменяет сетевой доступ; игровые сессии и браузеры не используются.
Workflow `offline-safety-tests` выполняет эти проверки без игровых секретов.

После проверки ветки облачное обновление должно переходить на новые файлы
после завершения текущих сеансов. Их отмена и параллельный запуск второй
сессии одного героя для обновления не нужны. `agent-vagojan` остаётся без cron.
Фактический переход проверяется по `head_sha` следующих трёх workflows.
Результат рейда подтверждается составом, действиями каждого героя,
оставшимся HP и итогом попытки, а не только зелёным статусом GitHub Actions.

Изменения разработаны Codex. Успешных вызовов Router Chip в этой среде не было.

## Доказательства исхода дракона

`raid_evidence.py` читает процент HP только рядом с `dragon_mif.png`, число
воинов/медиков и таймер из фактической структуры сохранённых страниц игры.
Каждые 15 секунд и при изменении состава/HP агент пишет `рейд: замер` и
сохраняет последние 120 замеров в runtime. В журнал попадают только параметры
и строки боя: HTML, ссылки, формы, чат и данные сессии не сохраняются.
Процент HP отделён от абсолютного `boss_hp`; округлённые 0% сами по себе
не доказывают убийство.

Смерть одного героя не завершает командный бой. Явная надпись о победе или
гибели отряда ищется в боевой области, независимо от длины подвала страницы.
Перед навигацией после паузы сохраняется последний ответ боя. Ни отсутствие
действий, ни истечение лимита ходов не считаются подтверждённым исходом.

`healing_requests` — отправленные нажатия лечения; `healing_lower_bound` —
сумма распознанных сообщений о фактическом лечении. Урон также является
нижней оценкой: полностью одинаковые повторяющиеся окна журнала нельзя
надёжно отличить от старого ответа сервера. Окна сравниваются с перекрытием,
так что одинаковые удары с разными соседними событиями больше не теряются
из-за глобального множества уникальных строк. Состояние переживает перезапуск.

Руководитель читает счётчик убитых драконов клана до старта и после попытки
в отдельной вкладке без ухода из боя. У ОК остаётся основной канал боевых
замеров. Рост счётчика подтверждает убийство кланом, но без боевого результата
не приписывается автоматически нашей тройке. До фактического результата
оценка силы остаётся «недостаточно данных». Проигрыш при неработающем лечении
сам по себе не доказывает необходимость четвёртого героя.

Пути трёх облачных конфигов явно считаются от корня репозитория
(`paths_relative_to: repository`). Это исключает ошибочную запись счётчиков
и журналов в `deploy/state` и `deploy/logs`, которые workflows не сохраняли.
Проверка использует настоящий `run.load_config`, а не только подменённый корень теста.

Если руководитель пропустил короткий закрытый период, он проверяет серверное
свидетельство другого нашего героя в `state/<account>/dragon-spawn.json`.
Каждый агент публикует собственные наблюдения закрытой пещеры с читаемым
таймером сразу, независимо от завершения workflow. Для восстановления нужны
наблюдение после последней попытки, уже наступившее серверное открытие,
текущая открытая пещера с живым драконом и заново проверенная готовность тройки.
Один локальный таймер не разрешает старт. При миграции принимается сохранённый
`raid_reopen_at` другого героя, полученный старой версией с реального таймера.
При отсутствии доказательства агент продолжает прочие разрешённые занятия,
а не держит бесконечную блокировку фарма.

Контрольная попытка 14.11.2026 в 12:35 МСК дала явный серверный итог
«Все воины убиты» при последнем наблюдаемом HP дракона 66%. Эта надпись
распознаётся как поражение; строка результата печатается компактно, чтобы
интерфейс журналов не обрезал исход после большого массива замеров.
Фактические сообщения боя используют «полечил» и могут не иметь clock2-иконок;
такие строки также учитываются, полученное лечение выделено отдельно.

Рейд может начаться до первого полного сбора состояния. Максимальные HP и
энергия сохраняются в runtime, а внутри попытки удерживается начальный/пиковый
заряд. Текущий опустевший заряд больше не становится новым максимумом
при каждом ходе. Это позволяет применять уже настроенный порог энергии
после запуска или перезапуска процесса без ухода из активного боя.

Публиковать переход действующих агентов на обязательную четвёрку следует после
проверки собственной игровой сессии ОК2, чтобы не оставить троих в ожидании
участника, который ещё не вошёл.

## Почтовая передача железа

Проверка реальной формы Кейса 14.11.2026 через сохранённый облачный доступ
показала только вариант «Мифрил» (`value=3`). Передача железа через эту форму

фактических названий вариантов: при отсутствии железа отправка запрещена.
